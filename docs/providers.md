# Providers

`LLMProvider` is the runtime boundary: `listModels(signal)`, `stream(request, signal)`, and optional observed `requestLimits(model)`. Normalized messages include structured tool calls and observations; events carry text, complete tool calls, usage, and completion reason. A new provider implements this contract without changing the agent loop.

The Groq adapter uses the official [Chat Completions API](https://console.groq.com/docs/api-reference). It discovers models dynamically, validates complete responses, propagates cancellation, bounds parser memory, and maps errors into safe product codes. Discovery transient failures receive short bounded backoff. Generation and resolved tool actions are never automatically replayed.

`SecretStore` isolates credential access. The host implementation delegates to [SecretStorage](https://code.visualstudio.com/api/references/vscode-api#SecretStorage); tests use an in-memory fixture. Do not implement plaintext file storage as a fallback. Credentials must never be sent to the UI.

The coding picker excludes speech, safety, embedding and hosted-agent systems, plus models explicitly lacking streaming or local tool support. Availability always comes from authenticated discovery. Published [model metadata](https://console.groq.com/docs/models) and [tool support](https://console.groq.com/docs/tool-use/overview) annotate known discovered coding models; newly discovered chat models keep unknown tool support. A saved compatible choice is retained; otherwise Little selects a discovered tool-capable default. Loading, timeout, empty catalog and failure states are visible. A transient refresh failure retains the valid cached catalog for the same credentials; changing keys or providers invalidates it.

The [live authenticated discovery probe](../desktop/logs/groq-live-models-success.json) returned four compatible coding models, including both GPT OSS 120B and 20B with tool-capable labels. It confirms discovery and records the owned extension host/window exit. It does not establish inference or every tool workflow for all discovered models.

GPT OSS 20B and 120B now use native local function calling and streamed answers. The shared [request builder](../src/little/providers/groq-request.ts) sends the original tool definitions, `tool_choice: auto`, and `parallel_tool_calls: false` for these models. It preserves assistant `tool_calls` and matched `tool_call_id` observations. The host validates and executes local tools sequentially. It sends no `response_format` for agent requests. See Groq's [local tool calling](https://console.groq.com/docs/tool-use/local-tool-calling) and [supported models](https://console.groq.com/docs/tool-use/overview).

The earlier strict decision wrapper caused schema rejection and `json_validate_failed` on repository questions, even after smaller fixture probes had passed. Simplifying that wrapper still produced unreliable generations. It has been removed rather than repaired from private failed output. Native tool calls are buffered through the complete response and checked before execution; malformed or incomplete calls cannot execute. Original tool argument validation, workspace boundaries, mode permissions, native diff review and command approval remain authoritative.

The full native wire body and completion reserve use the same builder for transport and budget. GPT OSS reserves up to 2,048 output tokens inside a conservative approximate 5,500-token request ceiling; other Groq models reserve 1,024. Observed model/account limits can reduce those budgets. Fresh source and recent tool evidence take priority over older observations. The UTF-8 estimate is conservative rather than an exact tokenizer. Optional tools and source may be shortened with visible notices.

GPT OSS uses `include_reasoning: false` and `reasoning_effort: low`, as documented in [Groq reasoning](https://console.groq.com/docs/reasoning). Hidden reasoning remains separate from user-facing answers. HTTP and SSE failures use bounded private classification: only fixed categories, known reason codes, numeric limits and validated request identifiers enter logs. Provider bodies, organization identifiers and `failed_generation` are never used as executable responses or displayed.

Quota headers pace subsequent requests with cancellable waits of at most 60 seconds. Longer waits become a visible model cooldown. **Prepare retry** restores the prompt for an explicit new submission. No generation or earlier action automatically replays. A different discovered model can have separate limits; request sizing cannot replenish an exhausted account allowance. See [Groq rate limits](https://console.groq.com/docs/rate-limits).

The exact reported prompt, `analyse the notebooks and codebase for me`, is tested against an owned notebook/Python fixture through native SecretStorage and the real provider/runtime. It checks actual source facts and cell citations, successful completion, bounded requests and exclusion of saved notebook output. This is separate from the packaged app's loopback smoke, which checks UI, cooldowns, parser failures, manual recovery and chat restart behavior. Live edits and approved checks on a full user repository remain broader acceptance work.

The [0.2.0 live file report](../desktop/logs/groq-file-live-acceptance.json) records five GPT OSS 120B flows: notebook/DOCX/PDF reads, a notebook edit proposal and whole-file slide deletion with metadata evidence. All 14 requests returned HTTP 200 and stayed within the approximate request ceiling. The test host rejected both proposals and verified unchanged original bytes. [15 native file cases](../desktop/logs/native-file-tools-smoke.json) separately exercised accepted edits/deletions, production review UI and exact-byte restoration with a scripted local provider. The final [30 native Groq/history checks](../desktop/logs/native-groq-smoke.json) passed on the same production bundle, including saved chats without request/action replay after restart. File tools and their format limits are described in [the workflow guide](file-tools.md).

[Saved chats](conversations.md) restore separately from executable run state. Their bounded recent completed turns may supply follow-up context; the current request budget accounts for them. Main-run token totals come from provider usage. Independent reviewer usage is separate and estimates are not billed usage.

The [Ollama adapter](../src/little/providers/ollama.ts) implements native `/api/tags` discovery and streaming `/api/chat` with NDJSON, complete tool-call buffering, usage and cancellation. The native host uses application-scoped provider settings and separate saved model choices for Groq and Ollama. API keys remain separate from provider configuration. The Settings gear switches providers; **Configure Ollama** accepts an already-running loopback origin, default `http://127.0.0.1:11434`. No models or runtimes are installed automatically. Discovery excludes declared remote/cloud proxy models and leaves tool capability unknown until verified. This does not prove an arbitrary local runtime is offline. See the primary [chat API](https://docs.ollama.com/api/chat), [model discovery API](https://docs.ollama.com/api/tags), and [tool calling documentation](https://docs.ollama.com/capabilities/tool-calling).

Both providers reject incomplete tool calls and do not replay generation or tool execution automatically. Ollama loopback HTTP fixtures exercise native framing and actual socket traffic; an installed model's real inference and broader model compatibility remain acceptance gates. Choose an installed tool-capable model for EDIT/AGENT.
