# Agent runtime

[AgentRuntime](../src/little/agent/runtime.ts) owns one run at a time. It collects context, streams normalized provider text, checks complete local tool calls, validates arguments and mode permissions, executes tools sequentially, returns sanitized observations and emits lifecycle events. Model prose cannot authorize a command or permission grant.

Groq uses native function definitions and canonical assistant/tool history. GPT OSS disables parallel calls. The adapter validates completion markers, offered tool names, object arguments and identifiers before releasing a call. Truncated, filtered, malformed or incomplete responses cannot release actions. For explicit file requests, speculative text is withheld until required evidence and action outcomes are observed, or the response honestly identifies a limitation. Grounded answers can stream. Host inspection gates, plans, native edit review, command grants and verification ledgers remain authoritative. See [providers](providers.md).

No live edit or command ran. These owned-fixture facts establish the tested flow rather than every possible repository answer.

Its final receipt includes confirmed cleanup and the initial cleanup-timing reconciliation described in [development](development.md). These accepted fixtures do not establish accepted live-model mutations or executed project checks.

[Saved conversations](conversations.md) persist display text separately from runtime events, grants and action ledgers. Recent completed turns may join a follow-up's context as bounded untrusted recollection. Restoring a chat never resumes execution.

## Modes and execution gates

| Mode | Available behavior |
| --- | --- |
| ASK | Inspect repository evidence and answer; SAFE tools only. Exact short standalone greetings omit repository context and tools. |
| PLAN | Inspect and produce a read-only implementation plan; SAFE tools only. |
| EDIT | Read tools plus bounded file proposals. Native diff review, explicit acceptance, and private checkpoints precede writes. No command execution. |
| AGENT | Read, publish a visible plan, propose reviewed edits, request approved project commands, inspect results, and attempt bounded repairs. |

Before AGENT can invoke a write or execution tool, it must obtain relevant tool evidence and publish `update_plan`. Source readers include `read_file`, `read_range`, `read_notebook`, `read_document`, `get_active_file`, `get_selection`, and matching source search. Initial context alone does not satisfy this gate. For explicit creation-only tasks, a listing of the actual target parent counts; `get_workspace_info` covers only root creation. For whole-file deletion, `inspect_file` size/hash metadata can count without a content read. Those exceptions do not satisfy existing-file edit or explanation requirements. Plans contain one to eight concise steps. The runtime enforces the prerequisites independently of the model's instructions.

## File request evidence and routing

[File workflow routing](../src/little/agent/file-instructions.ts) recognizes explicit file tasks and formats, and [RequestBudget](../src/little/context/request-budget.ts) retains the available relevant readers/proposal tools rather than dropping them as optional integrations. Identified literal paths are masked before action and semantic checks; the original target ledger, formats and workspace normalization remain intact. Thus `Delete slides.pptx.` permits metadata-first whole-file deletion, `Read scripts/update.ts.` does not request a mutation, and explicit cell deletion or reading before deletion still needs content. Notebook source uses one-based cells and focused lines; document text uses paragraph/slide/page citations. Regular-file metadata never establishes that its content was read. Text, notebook and document contents remain untrusted data. See [file-tools.md](file-tools.md) for supported operations, bounds and examples.

Each explicitly named target needs matching fresh evidence; editing needs content, creation needs its actual parent, and deletion may use metadata. Absolute paths inside the host's selected workspace normalize to relative targets; sibling/outside roots do not match. A completed text-only response that skips required evidence or reviewed actions gets one counted corrective continuation. The discarded speculative answer is not published or added as fabricated evidence. Another unresolved answer fails the run. This is a continuation of a valid response, not an automatic retry of a provider error.

Applied, rejected, conflicted, failed and cancelled proposal outcomes resolve the requested action attempt. A rejected or cancelled target cannot be resubmitted in that run, and an unperformed mutation claim receives the same bounded correction. Honest unavailable/unsupported disclosures and clarification for unidentified targets remain allowed; greetings and general knowledge retain their normal path. Routing and prose checks are bounded heuristics, while tool results, native approvals and verification cards remain authoritative. Fixed native validation guidance is redacted and bounded before returning to the model; unexpected or schema-library exceptions remain generic.

ASK/PLAN never gain write access. EDIT/AGENT mutations use native **Review diff → Accept changes**, with exact-byte private recovery for binary and deleted originals. Supported document operations are simple creation, DOCX/PPTX text replacement and PDF text-page append. Legacy DOC/PPT, encrypted files, OCR and in-place PDF layout/text replacement remain unsupported; text extraction/previews do not prove rendered layout.

The greeting shortcut applies only to ASK prompts of at most 40 characters matching `hi`, `hello`, or `hey`, with an optional `there`, `Little`, or `Little Code` and limited trailing punctuation. It skips context collection and offers no tools, while preserving provider generation, credential handling, request budgets, usage events, cancellation, and terminal state validation. The answer is not hardcoded. Task clauses, source paths, and other prompts use normal context and tools; PLAN, EDIT, and AGENT never take this shortcut.

Initial context uses the request to rank local repository metadata and select bounded fresh source excerpts with visible reasons and line citations. Broad codebase-overview requests prioritize root project anchors and diverse architecture paths rather than incidental About screens. `get_repository_map`, `find_relevant_files`, and `search_symbol` refresh protected inventory before returning metadata. These SAFE tools are eligible in every mode, subject to the request budget; repository-map metadata plus `update_plan` does not satisfy source inspection. Creation-parent and deletion metadata have the limited exceptions above. The [context pipeline](repository-context.md) shares a 20,000-character budget and separates unsaved active buffers from retrieved disk source.

Each file proposal still pauses for [native diff review](../src/extension/edit-review.ts). Each `run_command` request pauses for **Allow once** or **Reject**, with a further [native command confirmation](../src/extension/command-review.ts) before a private one-use grant is created. Rejection executes nothing. Approved project code runs with current-user OS permissions; working-directory checks are not an OS sandbox. See [tools.md](tools.md) for execution and checkpoint boundaries.

## Limits and cancellation

Defaults are 12 provider iterations, 16 tool requests per iteration, 64,000 serialized request characters including tool schemas, 32,000 answer characters per iteration, and 100,000 accumulated provider-reported input/output tokens. The desktop host supplies three minutes for ASK/PLAN and 15 minutes for EDIT/AGENT, including approval and quota waits. Each project command has its own one-to-120-second timeout. UTF-8 request estimates are conservative heuristics rather than provider tokenization.

[RequestBudget](../src/little/context/request-budget.ts) measures system/user messages, original tool schemas, source evidence, canonical tool observations and response reserve using the exact native Groq request builder. The conservative 5,500-token ceiling includes up to 2,048 GPT OSS output tokens or 1,024 for other Groq models. Other providers default to 24,000 including up to 2,048 output tokens. Model/account caps may lower these limits. Source and recent observations retain provenance; optional tools and older complete exchanges can be shortened with notices. Mandatory tools are retained or generation fails before submission. Compaction never changes action arguments, execution ledgers or permissions.

Large fresh observations are adaptively shortened against the actual escaped native wire before older exchanges are summarized. A bounded current source preview reaches the next request; omitted source remains unverified. The packaged native fixture checks that real read feedback reaches the model and that malformed calls, errors and explicit retries do not replay actions. See [the native report](../desktop/logs/native-groq-smoke.json).

Observed provider allowance can pause before the next request for at most 60 seconds per request, with **Stop** available and fresh headers rechecked after waiting. Longer allowance resets become actionable failures with a retry time. HTTP 429 generation is not retried automatically. The host binds cooldowns to the captured model/provider credentials, and **Prepare retry** restores the prompt for a new human submission. The UI separately displays actual provider-reported main-run usage. See [providers](providers.md).

A third identical validated non-command tool action ends the run; three consecutive tool exceptions also end it. Commands instead receive at most three attempts for the same program, arguments, and normalized working directory. Program identity is case-normalized, directory identity follows platform case rules, and changing `purpose` or timeout does not reset the allowance.

One AbortSignal covers context, provider, and tools. Stop cancels pending review and approval, and an executing command attempts to terminate its owned process tree. Tree-stop failure produces an explicit failure rather than a successful cancellation claim. Provider truncation, filtering, missing completion, and mismatched tool completion become errors; partial responses do not count as completed runs.

## Verification and observable state

The runtime records the latest result for each command identity. A check passes only when its latest result is `exited`, its exit code is 0, its output was not truncated, and it belongs to the current edit revision. Applied edits invalidate earlier results; accepted transactions that fail or are cancelled during apply/recovery also advance that revision. A later failed rerun replaces earlier success.

`agent.verification` reports `passed`, `failed`, or `not_run`, the observed command outcomes, and edits needing current verification. These are approved command-exit results, not a guarantee of overall project correctness. Failed checks can lead to `repairing`, another reviewed edit, and a fresh approved rerun within the same limits. Rejected, unavailable, cancelled, stale, and failed checks remain distinguishable.

[Runtime events](../src/little/shared/contracts.ts) also carry visible plans, context metadata, text deltas, tool activity, command proposals/results, and edit/checkpoint decisions. The [UI reducer](../src/little/ui/state.ts) ignores stale runs and late text after terminal states, while preserving matching late command exits and recovery events. The host keeps bounded event history for webview recreation. Saved display transcripts persist separately across restarts; executable event bindings and approvals do not.
