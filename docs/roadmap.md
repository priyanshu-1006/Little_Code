## Controlled Edit acceptance boundary

The integrated flow is: relevant file/parent inspection → structured text, notebook, document or whole-file-delete proposal → native diff review → explicit **Accept changes** or **Reject** → private `workspaceStorage` checkpoint → bounded mutations → restore card or **Little: Restore Checkpoint** command. New files need existing parent directories, proposals contain at most eight files, and dirty affected editors/notebooks must be saved first. Deletion metadata does not establish content inspection. Sensitive, ignored, generated, linked, and ignore-policy paths are excluded. Changed originals invalidate proposals; later user saves are preserved as restore conflicts. See [file tools and format limits](file-tools.md).

Original bytes and write-ahead mutation intents are persisted before workspace mutations. Actual child-process crashes test interrupted installation and restoration, including exact original bytes, changed identities, later deletions, ignore changes and corrupt storage. Recovery preserves ambiguity as a conflict and retains private/displaced originals. Windows power-loss durability and locks on external open-file handles or mutable ancestors are not guaranteed. Command side effects are outside these edit checkpoints; see [the recovery guide](checkpoints.md).

## Supervised Agent acceptance boundary

The AGENT flow is: inspect source → publish a visible plan → propose changes → native diff acceptance → request a structured project check → **Allow once** and native **Run command** confirmation → observed result → reviewed repair and fresh command approval when needed. Each exact check has at most three attempts; runs and command timeout/output are bounded. Copied, replayed, stale, and cancelled grants cannot authorize execution. ASK, PLAN, and EDIT do not expose commands.

Approved programs run with current-user OS permissions, including possible file and network side effects. They are not OS-sandboxed, and checkpoints do not roll back their side effects. Verification is limited to observed current checks: exit 0 with complete output, rejected/unavailable/failed checks, and stale checks after an accepted edit are represented separately. Fixture, temporary-process, and actual native approval/lifecycle tests cover the foundation. The live AGENT probe inspected an owned source fixture only; full live plan/edit/approved-check/repair behavior remains an acceptance gate. Reproduce the isolated native command check with `npm.cmd run desktop:smoke-commands`.

## MVP completion

PRD sections 82–83 define a larger MVP than the current ASK/PLAN, controlled EDIT, and supervised AGENT foundations: standalone IDE foundations, Groq streaming, complete file/patch tools, controlled execution, project context, permissions, cancellation, checkpoints, review, and verification.

The signature demo must inspect a real repository, propose a plan, create a checkpoint, implement authentication across files, run tests, diagnose and repair failures, rerun verification, and present the final diff. That demo is not complete yet.

Ollama, project/preference memory, approved loopback HTTP MCP, read-only Git review, bounded review workers and local browser snapshot inspection remain implemented foundations with earlier native acceptance. The 0.3 builder/runner/Flutter additions do not complete the signature Agent demo or installed-toolchain acceptance. Validate actual Ollama inference and fresh 0.3 provider/file regressions, then continue browser interaction, broader orchestration and PRD sections 84–86. The [installer guide](installer.md) records the current verified payload and artifact status. Installation/upgrade/uninstall, signing and a complete release audit remain before release readiness.
