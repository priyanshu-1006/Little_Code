# Development

## Primary deliverable: standalone Little Code

Little Code's product is its own Electron / Code-OSS desktop application. The Windows development package now launches independently from **LittleCode.lnk** or `.upstream/VSCode-win32-x64/Little Code.exe`; no installed editor or Node runtime is needed to open that executable. The bundled extension connects the host-neutral runtime and React UI to native editor services. An extension development host remains an optional integration-debugging workflow.

The pinned checkout lives in `.upstream/codeoss` and is excluded from source reviews and agent context. `codeoss.lock.json` records the exact official upstream commit. Preparation verifies that commit before applying product metadata and integration files; a mismatched checkout is not silently reset.

Follow the [official contributor instructions](https://github.com/microsoft/vscode/wiki/How-to-Contribute) and the pinned checkout's own configuration for complete component requirements.

### Controlled Edit milestone

EDIT's `propose_file_edits` accepts structured unique literal replacements, new UTF-8 files and whole regular-file deletion. Dedicated tools create/edit notebook cells, create DOCX/PPTX/PDF, replace DOCX/PPTX text, and append new PDF text pages. New files require an inspected existing parent. Text proposals are bounded to eight files, 32 replacements per file, 256 KiB per text file, and 1 MiB of combined text originals/proposals. Binary staging/deletion uses separate 16 MiB per-file and 32 MiB total checkpoint limits. Save affected dirty editors/notebooks before staging, acceptance, or restoration. See [file-tools.md](file-tools.md).

The model stages a proposal without writing repository files. **Review diff** opens original/proposed text or format-derived summaries in native diff editors. Only the host can mint acceptance, after that review and the user's **Accept changes** decision in a trusted workspace. **Reject** and cancellation while review is pending discard the proposal. ASK and PLAN cannot acquire this write permission. Binary bytes stay in the host; observations contain bounded outcomes, not document payloads. Text previews do not establish rendered Office/PDF layout.

The service rejects traversal, symlink/junction and hard-link aliases, sensitive/generated paths, `.gitignore` and `.littleignore` changes, and paths excluded by current root or nested ignore rules. It rechecks every original before beginning writes and each file before installation. A changed, deleted, or replaced original, including identical bytes on a different inode, invalidates the accepted proposal.

Before mutation, Little persists exact original bytes, including binary/deleted originals, and checkpoint metadata outside the repository in the extension's private `workspaceStorage` under its own app profile. The result card exposes **Restore changes** after a run finishes, or **Restore checkpoint** when recovery needs attention. **Little: Restore Checkpoint** discovers recorded checkpoints for the project after restart. Restoration checks the installed/deleted state and preserves later user changes as conflicts; unchanged states can still be restored. Checkpoint originals remain available when a conflict prevents restoration.

Filesystem tests cover exact original bytes, forged/reused acceptance, policy boundaries, changed originals, concurrent saves, cancellation and reopening. Version 2 write-ahead mutation intents make interrupted apply/restore records discoverable before workspace mutations; actual abrupt child-process exits exercise move/link/unlink/manifest/cleanup boundaries. Native restoration requires confirmation, trust, the same active project and clean affected editor buffers. Later deletions and saves remain protected conflicts. Windows directory flushing and external-process/ancestor locking are not guaranteed; see [checkpoint recovery](checkpoints.md) for precise durability limits.

File-routing tests require actual requested-file content, the correct creation parent or deletion metadata before reviewed actions. Literal identified paths are masked before intent checks, preserving original targets/formats: `Delete slides.pptx.` uses metadata-first whole-file deletion, `Read scripts/update.ts.` does not request a mutation, and explicit cell deletion or reading before deletion still needs contents. Tests also cover one withheld-answer correction, cancellation, rejection without resubmission, supported format schemas within the 5,500/2,048 Groq budget, and absolute-path normalization within the exact selected root. Greetings, general knowledge, clarification and honest unsupported-operation disclosures remain available. DOCX/PPTX reads and text replacements, notebook focused ranges/patches, and PDF generation/extraction passed deterministic file fixtures and accepted native reviews; OCR, legacy/encrypted formats, arbitrary binary editing and in-place PDF layout replacement are unavailable. Live notebook/DOCX/PDF reads and rejected notebook/PPTX-deletion staging pass separately; live PPTX content coverage and accepted live mutations/checks remain pending.

### Supervised Agent milestone

AGENT must inspect repository evidence and publish one to eight visible plan steps before proposing an edit or command. Its bounded tool loop can request reviewed changes, run approved project checks, inspect failures, propose reviewed repairs, and rerun affected checks. Every edit uses the same native diff/acceptance/checkpoint flow as EDIT. Every command requires a separate approval; a plan or previous Allow once never authorizes a later command.

The `run_command` tool takes a supported program, separate argument tokens, a relative project folder, a purpose, and a timeout. Programs are limited to npm/pnpm/yarn/bun test or run actions, Node local scripts/tests, Python pytest, pytest, Cargo checks/build/tests/formatting, Go checks/build/tests/formatting, .NET checks/build/formatting, TypeScript, and Git status/diff. Direct shell syntax, inline eval/print, package installation, destructive actions, network command programs, explicit parent/absolute paths, and detected credential flags/values are rejected; the displayed purpose is redacted. Arguments are bounded to 32 tokens of 512 characters; timeout is 1–120 seconds, defaulting to 60 seconds. The project toolchain must already be available on PATH.

The command card shows the exact program/arguments, folder, purpose, and timeout. **Allow once** opens a native **Run command** confirmation before the host mints a private one-use grant. Rejecting either confirmation starts no process. Grants are bound to the immutable proposal, executable, project folder/root identity, and active cancellation signal; copied, replayed, stale, or cross-proposal grants are rejected. Only AGENT exposes command execution; ASK, PLAN, and EDIT cannot acquire it.

Commands retain the current user's OS permissions. Project scripts can write outside the launch folder, access the network, or perform other side effects; this is not an OS sandbox. Checkpoints cover accepted file edits, not command side effects. Environment cleanup and output secret redaction are heuristic protection, not filesystem or credential isolation. Windows npm/TypeScript shims use restricted, quoted `cmd.exe` invocation; direct shell input remains unavailable.

Stdout/stderr are captured with a 64 KiB byte ceiling and 16,000-character display ceiling, with redaction and terminal-control cleanup before exposure. Results include status, exit code, duration, and truncation. **Stop**, command timeout, excessive output, and host disposal request process-tree termination. Windows stop results wait for `taskkill /t /f`; a failed tree confirmation is reported as failure rather than claimed as a successful stop. Normal parent/descendant termination is tested, but deliberately detached or escaped descendants are not an isolation guarantee. The **Little Commands** output channel retains observed command output.

The runtime limits a run to 12 model iterations, three attempts per exact program/arguments/folder, and a 15-minute Agent run deadline including approval waits. Accepted edits and failed/cancelled accepted edit transactions invalidate earlier checks. A check passes only with `exited`, exit code 0, and no output truncation on the current edit revision. Rejected, cancelled, failed, malformed, thrown, and stale checks cannot inherit an earlier success. The verification card reports recorded checks; it does not prove overall correctness or changes made outside Little's edit tracking.

Deterministic providers and real temporary-process fixtures cover the inspect/plan prerequisites, approved edit/check/repair/rerun flow, retry limits, honest verification, token/path/credential rejection, Windows npm shims, one-use approval, cancellation, timeout, bounded output, and descendant termination. The real packaged native command-host smoke separately passed rejection, two actual native confirmations, approved Node execution, replay denial, pending cancellation, executing disposal/no late write, closed-host denial, and clean owned-process exit. This harness uses a disposable normal extension under an isolated profile because upstream extension-test mode intentionally disables dialogs; it does not modify the product or connect a provider. Live Groq/model behavior and the full repository Edit/Agent human flow remain separate acceptance work.

Its narrow-layout check emulates a 900×800 native renderer viewport; it does not claim a physical-window or high-DPI test. See [shell evidence](../desktop/logs/native-shell-smoke.json), [dark screenshot](../desktop/screenshots/native-shell-dark.png) and [light screenshot](../desktop/screenshots/native-shell-light.png). The command-host smoke also uses an isolated generated profile/project, confirms only its observed fixture dialogs, tests actual host approval/process lifetime, and writes `desktop/logs/native-command-host-smoke.json`. The feature smoke uses genuine UI actions with local provider/MCP fixtures and restarts the same private profile to check persistence; `--browser` adds an owned isolated Chrome process and native inspection consent/editors. The Chromium protocol smoke requires installed Chrome and verifies target cleanup and navigation boundaries independently. These checks use no real API key or model download. The terminal smoke runs that same executable as Electron Node, loads the packaged native `node-pty`, and checks actual PowerShell PTY data/exit events within 20 seconds. It records the Electron version, native ABI, module path, marker, and exit in `desktop/logs/native-terminal-smoke.json`. `--source` is available for the owned source-runtime ABI check while packaging is in progress.

The packaged terminal backend check establishes native PTY compatibility; the command runner has separate approval and process-lifecycle checks. These recorded foundations do not complete the PRD's real-repository demo or release validation.

`scripts/update-desktop-shell.mjs` can refresh an existing package from a successful pinned `--nls` native build. It verifies the ten canonical integrity checksums and indexed-localization metadata, writes resources atomically, and preserves the executable/runtime and running processes. This update requires a full app restart. A full `desktop:build` uses canonical packaging and replaces the output folder, so close Little Code before running it.

Packaged releases must retain Code-OSS's open-source license and required notices, carry Little platform icons and distribution identifiers, and complete the distribution/service configuration audit. The separate [per-user setup build](installer.md) produces an unsigned development installer; compiler and payload checks do not establish installation/upgrade/uninstall behavior or release readiness.
